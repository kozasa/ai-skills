# Review Loop（レビュー収束ループ）

## 目的

実装完了後の「レビュー → フィックス」を、高確信度の指摘がゼロになるまで自動で繰り返す。
モデルの自己申告による早期終了を防ぐため、以下の手順と禁止事項に厳密に従うこと。

## レビュー対象

現在のブランチと `main`（存在しなければリポジトリのデフォルトブランチ）の差分、および未コミットの変更。

## 準備

1. ラウンド番号 R = 1 とする。
2. ログファイルを作成する:
   `~/.review-loop/logs/<リポジトリ名>/$(date +%Y-%m-%d-%H%M%S).md`
   （ディレクトリがなければ `mkdir -p` で作成）
3. quality gates を特定する: `package.json` / `Makefile` / CI 設定 /
   プロジェクトの `CLAUDE.md` / `AGENTS.md` を確認し、テスト・ビルド・リンタの
   実行コマンドを決める。見つからない場合はユーザーに一度だけ確認する。

## ループ手順（R = 1..最大6）

### 1. レビュー（フレッシュな目で実行する）

- **Claude Code の場合**: Skill ツールで `code-review` を起動する（effort: medium）。
  自分の記憶や直前の作業内容からの推測でレビューを代用してはならない。
- **Codex の場合**: 実装時の記憶を根拠にせず、`git diff` を最初から読み直して
  独立したレビューを行う。観点: (a) バグ・ロジック誤り (b) エッジケース・エラー処理
  (c) セキュリティ (d) 既存コードとの不整合 (e) テストの妥当性。
  `codex exec` によるフレッシュインスタンスでのレビューが可能な環境ならそちらを優先する。

### 2. 分類

各指摘を次の2つに分類し、指摘の全文と分類理由をログファイルに追記する:

- **high**: バグ・明確な問題。修正しないと動作・品質に実害がある。→ フィックス対象
- **low**: 好み・提案・確信の持てない指摘。→ 修正せず「見送りリスト」へ

### 3. 終了候補・上限判定

- high がゼロ → フィックスを行わず手順5へ進む。この時点では終了しない。
- 前のラウンドと同一の high が再出現 → 打ち切り理由を記録し、フィックスせず手順5へ進む（修正できていない、または修正が振動している）。
- R = 6 かつ high が1件以上なら、打ち切り理由を記録し、フィックスせず手順5へ進む。R6は確認レビュー専用とする。
- それ以外 → 手順4へ進む。

### 4. フィックス

high の指摘のみ修正する。low は絶対に修正しない。
修正内容（何をどう直したか）をログファイルに追記する。

### 5. 検証と正常終了判定

high の有無にかかわらず、毎ラウンド quality gates（テスト・ビルド・リンタ）を実行する。

- 手順3で打ち切り理由を記録済み → gates の結果もログに残して **打ち切り**。残ったhighと、失敗したgatesがあれば未解決の指摘として報告する。
- R = 6 で quality gates が失敗 → 追加修復せず **打ち切り**。失敗内容を未解決の指摘として報告する。
- high がゼロかつ quality gates が追加修復なしで成功 → **正常終了**。「終了時レポート」を出して終わる。
- quality gates が失敗 → このラウンド内で修復し、修復内容をログに残す。修復後に gates が成功しても正常終了せず、再レビューのため手順6へ進む。
- それ以外 → 手順6へ進む。

### 6. ラウンド制御

R を +1 して手順1へ戻る。

## 禁止事項

- レビューを実際に実行せずに「指摘なし」と判断すること。
- low の指摘を修正すること。
- ループ内で git commit を行うこと（終了時に提案のみ）。
- 上限（フィックス5回）を超えて回し続けること。R6ではフィックスしない。
- 打ち切り時に、残った指摘を報告せずに終わること。

## 最終マージ判定

終了状態から次の優先順位でAIの推奨判定を1つ決める。

1. **マージ非推奨**: high が残る、必須 quality gate が失敗している、またはループを打ち切った。
2. **条件付きマージ**: high はゼロだが、手動確認、外部環境での確認、または未実行の必須 quality gate が残る。
3. **マージ推奨**: high がゼロ、すべての必須 quality gates が成功し、未確認の必須事項がない。

low の指摘だけを理由に判定を下げない。AIの判定は推奨であり、最終的なマージ判断は人間が行う。

最終応答は必ず `## 最終マージ判定: <判定>` という文字列から開始する。この見出しより前には、空行を含めて何も出力しない。挨拶、要約、レビュー結果、ツール実行やスキル読み込みの経緯、注意書きもすべて判定見出しの後に置く。

- `理由`: 判定を決めた事実を1文で書く。条件付きでは残る確認事項、非推奨ではブロッカーを具体的に書く。
- `人間の最終確認`: マージ前に人間が確認または実行すべき項目を具体的に書く。

## 終了時レポート（必須・この形式で出力する）

```
## 最終マージ判定: [マージ推奨 / 条件付きマージ / マージ非推奨]

理由: <判定を決めた事実を1文で記載>
人間の最終確認: <マージ前に確認または実行すべき具体的項目>

## review-loop 結果: [収束 / 打ち切り（理由）]
実行ラウンド数: N / ログ: <ログファイルパス>

### フィックスした指摘
- [R1] <指摘> → <対応>
...

### 見送った低確信度の指摘
- <指摘>（見送り理由）
...

### 未解決の指摘（打ち切り時のみ）
- <指摘>
...

### 次のアクション提案
- コミット: <提案するコミットコマンド>（実行はユーザー承認後）
```
