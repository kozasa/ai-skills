# Review Loop（レビュー収束ループ）

## 目的

実装完了後の「レビュー → フィックス」を、今回の変更を止めるブロッカーがゼロになるまで自動で繰り返す。
モデルの自己申告による早期終了を防ぐため、以下の手順と禁止事項に厳密に従うこと。

## 再帰ガード

タスクに `[review-loop-child]` が含まれる場合、このスキルの親ループから起動された
レビュー専用プロセスである。`review-loop` や別の `codex exec` を起動してはならない。
差分を読み取り専用で1回だけレビューし、指定された形式で指摘を返して終了する。

## レビュー対象

R1は変更全体を対象とする。R2以降は修正差分と影響範囲に絞り、同じ変更の完了に必要な確認を行う。

## 準備

1. ラウンド番号 R = 1 とする。
2. ログファイルを作成する:
   `~/.review-loop/logs/<リポジトリ名>/$(date +%Y-%m-%d-%H%M%S).md`
   （ディレクトリがなければ `mkdir -p` で作成）
3. quality gates を特定する: `package.json` / `Makefile` / CI 設定 /
   プロジェクトの `CLAUDE.md` / `AGENTS.md` を確認し、テスト・ビルド・リンタの
   実行コマンドを決める。見つからない場合はユーザーに一度だけ確認する。
4. R2以降へ渡す対象パスを記録する欄をログに用意する。フィックスで実際に変更したファイルと、
   その修正の安全性を判断するため直接確認が必要な変更済みファイルだけを対象にする。

## ループ手順（R = 1..最大6）

### 1. レビュー（フレッシュな目で実行する）

- R1は現在のブランチと基準ブランチの差分、および未コミット変更の全体をレビューする。
- R2以降は直前のフィックスで記録した対象パスだけをレビューする。新しい機能や無関係な箇所を
  探索し直すラウンドにはしない。ただし、対象パス内で修正が生んだ副作用は報告する。

- **Claude Code の場合**: Skill ツールで `code-review` を起動する（effort: medium）。
  自分の記憶や直前の作業内容からの推測でレビューを代用してはならない。
  R1は対象なしで起動する（2.1.329以降、対象なしは多くのモデルでブランチ全体を既定ブランチと
  比べてレビューし、複数commitで差分を失う不具合も同じ版で直った）。追跡中ファイルの未コミット変更は
  含まれるが、未追跡ファイルは含まれないため、R1の前に `git status` で未追跡ファイルが無いか確かめ、
  あれば `git add -N <path>` してから起動する。
  ただし `code-review` の指示（Phase 0）の引用では、対象なしは upstream があればそれと比べるとあり、
  CHANGELOG の「既定ブランチと比べる」と食い違う。そのため R1 の前に
  `git rev-parse --abbrev-ref @{upstream}` と既定ブランチ（`git rev-parse --abbrev-ref origin/HEAD`）を確かめ、
  対象なしで起動するのは両方が基準ブランチ（`origin/main` 等）と一致するときだけにする。
  どちらかが基準ブランチと違う（push 済みの同名ブランチ、基準が `origin/release` で既定が `origin/main` など）か
  取れないときは、比べる相手を `code-review` に任せず親の側で固定する。親が三点差分
  `git diff <基準ブランチ>...HEAD` と未コミット変更 `git diff HEAD`（未追跡ファイルは先に `git add -N`）を
  リポジトリの外の一時ファイルに書き出し、その差分ファイルを対象として渡す。
  例: `medium <差分ファイル> この差分ファイル（基準ブランチ <基準ブランチ> との三点差分と未コミット変更）の変更をレビューする`。
  R2以降は、記録した対象パス（準備の手順4の欄）を `code-review` の対象として並べて渡す。
  例: `/code-review medium <path1> <path2>`（Skill ツールなら args に `medium <path1> <path2>`）。
  Codex の `--focus-path` と同じ考え方で、対象パスの外を探索し直すラウンドにしない。
  出典: https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md#21329
  （これより古い Claude Code では対象なしの挙動が違う）。
- **Codex の場合**: 毎ラウンド、必ず `codex exec` を起動し、フレッシュインスタンスで
  独立したレビューを行う。現在のセッションによる自己レビューへフォールバックしてはならない。
  `scripts/codex_review.py` を使い、親側で固定したdiffを空の一時ディレクトリの子Codexへ渡す。
  子Codexには追加探索しないよう指示するが、read-only sandboxはOSレベルのファイル読み取り禁止を
  保証しない。親側で `codex exec` を直接組み立ててはならない。
  観点: (a) バグ・ロジック誤り (b) エッジケース・エラー処理 (c) セキュリティ
  (d) 既存コードとの不整合 (e) テストの妥当性。
  ラウンド固有の結果ファイルを指定して次の形式で実行する:
  `python3 <skill-dir>/scripts/codex_review.py --repo <repo-root> --base <base-branch> --round <R> --output <result.json>`。
  R2以降は、記録した各対象パスを `--focus-path <repo-relative-path>` として繰り返し指定する。
  モデルと深さは既定で `gpt-6.2-sol` / `high` に固定しており、`--model` / `--effort` で変えられる。
  `--timeout` の既定は600秒。Codexが `not supported` で失敗したら、`codex --version` を確かめ
  CLIを0.169.1以上に上げる（`-c` を外してやり直さない）。
  ランナーは `[review-loop-child]`、`--ephemeral`、read-only sandbox、空の作業ディレクトリ、
  merge-base以降のbranch差分とHEAD以降の未コミット差分を分けた固定diff入力（通常文脈10行）、
  標準出力の抑制、構造化出力、Codexのturn入力上限を下回る
  1,000,000文字のpacket上限、タイムアウト、終了コード、
  非空結果を強制する。
  プレビュー等の未追跡コピーが入力を肥大化させる場合は、
  `--reference-unchanged-copies` を指定できる。merge-base以降とHEAD以降のどちらでも
  変更されていない通常ファイルのGit blobとバイト一致するコピーだけを、元パス・blob ID・
  SHA-256付き参照に置換する。新規ファイルのパスは残し、変更・新規実装の本文は省略しない。
  参照化した既存本文は再レビューしていないことをログに明記し、新パスでの使用箇所は確認する。
  上限自体は引き上げない。上限超過の改善後は新しいログでループを再開できる。
  ランナーが失敗した場合は、理由をログに記録し、
  **打ち切り（独立レビューを実行できない）** とする。

### 2. 分類

各指摘を次の3つに分類し、指摘の全文と分類理由をログファイルに追記する。
ラウンド番号、修正難度、残り時間を理由に分類を下げてはならない:

- **ブロッカー**: この変更を今マージすると安全性、データ、認証、中心機能、または変更目的に
  重大な実害が出る明確な欠陥。→ ループ内のフィックス対象
- **フォローアップ**: 実害のある明確な欠陥だが、影響が限定され、今回の変更を危険にせず
  独立して追跡・修正できるもの。→ 今回は修正せず、重複を除いて後続課題へ
- **提案**: 好み、改善案、または確信の持てない懸念。→ 修正せず見送りリストへ

### 3. 終了候補・上限判定

- ブロッカーがゼロ → フィックスを行わず手順5へ進む。この時点では終了しない。
- 前のラウンドと同一のブロッカーが再出現 → 打ち切り理由を記録し、フィックスせず手順5へ進む（修正できていない、または修正が振動している）。
- R = 6 かつブロッカーが1件以上なら、打ち切り理由を記録し、フィックスせず手順5へ進む。R6は確認レビュー専用とする。
- それ以外 → 手順4へ進む。

### 4. フィックス

ブロッカーのみ修正する。フォローアップと提案はループ内で修正しない。
修正内容（何をどう直したか）と、次のラウンドで確認する対象パスをログファイルに追記する。

### 5. 検証と正常終了判定

ブロッカーの有無にかかわらず、毎ラウンド quality gates（テスト・ビルド・リンタ）を実行する。

- 手順3で打ち切り理由を記録済み → gates の結果もログに残して **打ち切り**。残ったブロッカーと、失敗したgatesがあれば未解決の指摘として報告する。
- R = 6 で quality gates が失敗 → 追加修復せず **打ち切り**。失敗内容を未解決の指摘として報告する。
- ブロッカーがゼロかつ quality gates が追加修復なしで成功 → フォローアップを重複排除し、
  フォローアップごとに Beads の既存課題を検索する。既存課題があればIDを記録し、なければ
  新規課題を作成してIDをログへ残したうえで **正常終了** する。Beadsを利用できない場合は、
  終了時レポートの人間の最終確認へ各項目を残す。
- quality gates が失敗 → このラウンド内で修復し、修復内容をログに残す。修復後に gates が成功しても正常終了せず、再レビューのため手順6へ進む。
- それ以外 → 手順6へ進む。

### 6. ラウンド制御

R を +1 して手順1へ戻る。

## 禁止事項

- レビューを実際に実行せずに「指摘なし」と判断すること。
- Codex で `codex exec` を実行せず、現在のセッション内のレビューで代替すること。
- フォローアップまたは提案をループ内で修正すること。
- ラウンド数や修正の難しさを理由にブロッカーをフォローアップへ下げること。
- ループ内で git commit を行うこと（終了時に提案のみ）。
- 上限（フィックス5回）を超えて回し続けること。R6ではフィックスしない。
- 打ち切り時に、残った指摘を報告せずに終わること。

## 最終マージ判定

終了状態から次の優先順位でAIの推奨判定を1つ決める。

1. **マージ非推奨**: ブロッカーが残る、必須 quality gate が失敗している、またはブロッカーを理由にループを打ち切った。
2. **条件付きマージ**: ブロッカーはゼロで必須 quality gates は成功したが、フォローアップだけが残る、
   または手動確認・外部環境での確認・未実行の必須 quality gate が残る。
3. **マージ推奨**: ブロッカーとフォローアップがゼロ、すべての必須 quality gates が成功し、未確認の必須事項がない。

提案だけを理由に判定を下げない。フォローアップは追跡先が確保されている場合に限り
条件付きマージにできる。AIの判定は推奨であり、最終的なマージ判断は人間が行う。

## 正常・条件付き終了後の human-handoff

この終了後フローは **Codex / Claude Code 共通** とする。

最終マージ判定が **マージ推奨または条件付きマージ** の場合、終了時レポートを確定した後、
最終応答を返す前に `human-handoff` スキルが利用可能か確認する。利用可能なら必ず起動し、
レビュー対象の変更概要、フィックス内容、quality gates の結果、最終マージ判定、ログパス、
人間の最終確認項目を引き渡す。条件付きマージでは、残っている確認事項と、確認後に
マージ可能になる条件を handoff の中心にする。

`human-handoff` が利用できない場合はエラーにせず、通常の終了時レポートを返す。
`human-handoff` の起動または成果物生成が失敗した場合もレビュー結果は失わず、失敗理由を
終了時レポートに短く追記して Markdown で完了する。**マージ非推奨では起動しない**。

`human-handoff` はレビュー判定を変更しない。handoff 後も、最終応答は下記の判定見出しから
開始し、生成した handoff 成果物があれば終了時レポート内から参照できるようにする。

最終応答は必ず `## 最終マージ判定: <判定>` という文字列から開始する。この見出しより前には、空行を含めて何も出力しない。挨拶、要約、レビュー結果、ツール実行やスキル読み込みの経緯、注意書きもすべて判定見出しの後に置く。

- `理由`: 判定を決めた事実を1文で書く。条件付きでは残る確認事項、非推奨ではブロッカーを具体的に書く。
- `人間の最終確認`: マージ前に人間が確認または実行すべき項目を具体的に書く。

## 終了時レポート（必須・この形式で出力する）

```
## 最終マージ判定: [マージ推奨 / 条件付きマージ / マージ非推奨]

理由: <判定を決めた事実を1文で記載>
人間の最終確認: <マージ前に確認または実行すべき具体的項目>

## review-loop 結果: [収束 / 打ち切り（理由）]
実行ラウンド数: N / ログ: <ログファイルパス>

### フィックスした指摘
- [R1] <指摘> → <対応>
...

### 後続課題へ移したフォローアップ
- <指摘> → Beads <issue-id>（Beadsを利用できない場合は人間の最終確認へ記載）
...

### 見送った提案
- <指摘>（見送り理由）
...

### 未解決の指摘（打ち切り時のみ）
- <指摘>
...

### 次のアクション提案
- コミット: <提案するコミットコマンド>（実行はユーザー承認後）
```
